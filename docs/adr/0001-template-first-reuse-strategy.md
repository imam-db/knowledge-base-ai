# Template-First Reuse Strategy

For the first two to three Knowledge Applications, reuse happens through a **template repository**, not a shared package. This repo becomes that template after cleanup: domain samples and hard-coded persona are generalized into **neutral but runnable** defaults, the repository is renamed to **`knowledge-application-template`** (local path and remote), then a template baseline is tagged (for example `template-v1`). After that tag, **Knowledge Base AI is forked into its own product repository** so template and product have clear, separate lifecycles. No automatic upstream sync is required yet; important foundation fixes are ported manually until a later `rag-core` extraction. Git history may still show the Knowledge Base AI origin; no history rewrite is required.

Cleanup is **not** a rewrite. Prefer the smallest change that separates Foundation from Domain Layer while the app keeps working. New thin interfaces (`LLMProvider`, `EmbeddingProvider`, `ChromaStore`) may land under `app/core/`; existing modules stay put and migrate only when stable. Folder beauty is not a goal.

The Reusable Foundation stays a **logical core inside the template**. Thin provider interfaces may live there; pluggable retrieval strategies do not until proven. A `rag-core` package is extracted only after the same foundation code proves stable across multiple real applications (and still only for pieces that vary by configuration, not strategy). Rejected for now: extracting a package from project one, keeping product #1 on a long-lived branch or dual-identity in the template repo, a monorepo of apps sharing one core, and enterprise folder churn for its own sake.
